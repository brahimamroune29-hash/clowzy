# مراجعة Clowzy — 2 أكتوبر 2026

## 1. النتيجة والنطاق

راجعت التطبيق الحالي في outputs/wasl-platform: API، المصادقة والاستعادة، الصلاحيات، الرصيد، البحث ودورة المزود، قراءة المواقع، المساعد، التصدير، الواجهات، مخطط القاعدة، الاختبارات وإعدادات النشر والمراقبة.

البنية: Next.js 16.3.6 وReact 19.3.0، Postgres عبر postgres.js ودور تطبيق مخصص، Icypeas للبحث والتحقق، Claude Haiku عبر OpenRouter للربط اللغوي والمساعد. ترحيل GPT-6 ما زال خطة؛ لم ينفذ ضمن هذه المراجعة.

التقييم: أساس جيد للتحقق من الرصيد والعزل على مستوى التطبيق، لكن توجد مخاطر تشغيلية وأمنية باقية، أبرزها DNS rebinding في قراءة المواقع وتزامن العمل مع مزود مدفوع. لا أعتبر الاختبارات المحلية شهادة أمان للإنتاج.

أُصلحت محليًا حدود الطلبات بين نسخ الخادم، ذرية عمليات الدخول وكلمات المرور والاستعادة، تصنيف عناوين داخلية إضافية، وحماية CSV من سطر جديد في بداية الخلية. لم أنشر التغييرات ولم أغيّر قاعدة إنتاج أو مفاتيح أو حسابات أو DNS. حُفظت التغييرات السابقة في README.md وvercel.json.

الحدود: لا اختبار اختراق حي، لا فحص صلاحيات قاعدة الإنتاج، لا اتصال مدفوع بالمزود أو AI، لا فحص شامل لكل تاريخ Git، ولا اختبار واجهات تفاعلي في متصفح. فُحصت الشفرة الحالية والاختبارات والإعدادات؛ المظهر وتجربة لوحة المفاتيح تحتاج تجربة مستقلة.

## 2. سطح الهجوم وتدفق البيانات

- المتصفح ← API: ملف ارتباط HttpOnly، sameSite=strict، Secure عند APP_URL عبر HTTPS، بوابة host/origin، حد جسم 64 KB، والتحقق عبر Zod.
- الدخول والدعوات والاستعادة: كلمات مرور scrypt مع salt، رموز عشوائية تُخزن مجزأة، انتهاء صلاحية وقبول مشروط مرة واحدة.
- المشترك ← بحث: قبول الشروط، حل الجمهور، حجز الرصيد، حفظ حالة المزود، إرسال دفعة، polling، ثم حفظ البريد وخصم الرصيد داخل معاملة.
- الشركة ← موقع خارجي: safeGet يقرأ الصفحة العامة والاتصال والredirects؛ المحتوى والعناوين الخارجية حدود ثقة مهمة.
- النص العربي ← OpenRouter: لا أدوات لتنفيذ عمليات نيابة عن المساعد؛ النتائج تخضع للقوائم والتحقق قبل الاستخدام.
- التصدير: تصفية الملكية على الخادم ثم CSV. الإدارة تتحقق من الدور في API وStore.
- قاعدة البيانات: عزل المستخدمين عبر شروط user_id في التطبيق. عدم وجود RLS في schema.sql ليس وحده دليل تسرب؛ صحة حماية مخطط clowzy ودور الاتصال تحتاج فحصًا في بيئة اختبار.

## 3. النتائج الأمنية حسب الأولوية

### S1 — DNS rebinding في قارئ المواقع: عالية، مسار محتمل، ما زال مفتوحًا

الموقع: src/lib/site-email.ts، safeGet. يتم lookup وفحص IP ثم fetch بالاسم، فيستطيع اتصال fetch إجراء حل DNS آخر مختلف. التعليق الحالي يقر بهذا الحد.

الأثر الواقعي: إذا ظهر موقع يتحكم فيه مهاجم ضمن بيانات الشركات، يمكن أن يحاول توجيه اتصال الخادم إلى شبكة داخلية. لا يوجد برهان استغلال حي أو تأكيد قابلية الوصول داخل بيئة النشر.

الإصلاح المطلوب: ربط الاتصال بالعنوان العام الذي فُحص باستخدام lookup مخصص في node:http/node:https أو transport مناسب مثبت، مع إبقاء hostname وHost وTLS servername والتحقق من الشهادة، وإعادة الفحص لكل redirect. حد شامل للوقت والبايتات، وإلغاء العمل عند نهاية الميزانية.

القبول: اختبار محلي يجعل الحل الأول عامًا والثاني داخليًا؛ لا اتصال داخلي ولا lookup ثانٍ عند الاتصال، مع نجاح HTTPS والredirect العام. لا يكفي فحص URL أو regex إضافي.

### S2 — نطاقات IP داخلية تفلت من التصنيف: عالية مشروطة بالشبكة، مؤكدة في المصنف، أُصلحت جزئيًا

الموقع: src/lib/site-email.ts، privateAddress. الصيغ IPv6 الموسعة مثل 0:0:0:0:0:0:0:1 وIPv4-mapped بصيغة hex لم تكن محظورة، وبعض نطاقات IPv4 الخاصة للاستخدامات الداخلية كانت تمر.

الإصلاح: قبول IPv6 global-unicast فقط وإضافة حظر 192.0.0.0/16 و198.18.0.0/15. هذه سياسة محافظة قد ترفض عناوين عامة خاصة الاستخدام؛ لا تعالج DNS rebinding في S1 ولا كل مسارات IPv6 الانتقالية المحتملة.

التحقق: توسعة tests/site-email.test.ts لتغطية الصيغ والنطاقات مع استمرار قبول عناوين عامة عادية. لا ادعاء بوصول فعلي إلى شبكة داخلية.

### S3 — حدود الطلبات في الذاكرة لكل نسخة: متوسطة، مؤكدة، أُصلحت

الموقع: src/app/api/[...path]/route.ts. Map مستقلة لكل عملية تسمح بتجاوز الحد الإجمالي مع توزيع الطلبات أو إعادة تشغيل الخادم. الأثر استنزاف المزود وAI والقاعدة من حساب مسجل.

الإصلاح: إعادة استخدام Store.hit في القاعدة للحد العام 120/دقيقة والبحث 20/دقيقة والعد 60/دقيقة، قبل الاتصال الخارجي؛ دون اعتماد جديد.

التحقق: اختبار journey يضع العدادات المشتركة عند الحد ثم يطلب API/search/count/search؛ يحصل على 429 دون استدعاء المزود أو المساعد. النوافذ ثابتة، وقد تسمح بضعف الحد حول حد الدقيقة؛ هذا الحد معروف وليس sliding window.

### S4 — سباقات عمليات كلمة المرور وروابط الاستعادة: متوسطة، مؤكدة من التسلسل، أُصلحت محليًا

الموقع: src/lib/store.ts، login/changePassword/createReset/createRecoveryCode/resetPassword.

قبل الإصلاح: تحقق كلمة المرور خارج معاملة التحديث، وإنشاء رابط الاستعادة يلغي القديم ويُنشئ الجديد بعمليتين منفصلتين. عند التزامن قد يبقى رابطان صالحان؛ فشل إنشاء الجديد قد يبطل القديم بلا بديل. وقد يصدر دخول متداخل مع تغيير كلمة المرور جلسة بعد إلغاء الجلسات.

الإصلاح: معاملة وقفل صف الحساب قبل تحقق كلمة المرور والتحديث وإصدار الجلسة أو الرمز؛ إنشاء reset وإلغاء القديم والتدقيق ذري؛ ترتيب الحساب ثم reset_tokens موحد لتقليل deadlocks.

التحقق: اختبار حقن فشل الإدخال يثبت بقاء الرابط السابق بعد rollback، والتحقق من قفل الحساب قبل لمس tokens، ونجاح تغيير واحد فقط عند إعادة استخدام كلمة المرور السابقة. PGlite يسلسل المعاملات؛ التزامن الحقيقي متعدد الاتصالات ما زال يحتاج قاعدة اختبار منفصلة.

### S5 — بداية LF في خلية CSV: منخفضة، فجوة معالجة مؤكدة، أُصلحت

الموقع: src/lib/csv.ts، cell. أضيف LF إلى الحروف التي تتطلب apostrophe في بداية الخلية، إلى جانب علامات الصيغ وTAB وCR. اختبار ينفذ حالة newline ثم صيغة. لا يثبت ذلك سلامة كل برنامج جداول أو كل إعادة استيراد/تصدير.

### ما لم يثبت كثغرة

الاستعلامات الحالية تمرر القيم كمعاملات؛ SQL الديناميكي في patch مصدر مفاتيحه الداخلي. ملكية البحث والتصدير ودور الإدارة مفحوصة وتغطيها اختبارات. React يعرض البيانات كنصوص، وdangerouslySetInnerHTML الوحيد في layout نص ثابت. CSP unsafe-inline يضعف الدفاع الإضافي لكنه ليس بمفرده إثبات XSS. بيانات المزود ليست سرًا بمجرد ظهور أسماء شركات، لكن تظل بيانات يجب حمايتها.

## 5. الاعتماديات والنشر

npm audit --json أعاد صفر تنبيهات لـ436 اعتمادًا. هذه نتيجة سجل npm وقت الفحص، وليست ضمانًا.

المصدر الرسمي بتاريخ 30 سبتمبر 2026 يوصي بالإصدار Next.js 16.3.8؛ الحالي 16.3.6. المصدر: https://nextjs.org/blog/september-2026-security-release

تسرب معلومات MCP في next dev متعلق ببيئة التطوير. SSRF الخاص بمُحسن الصور يتطلب remotePatterns غير موجودة هنا، ومشكلات use cache/Draft Mode لا تظهر في إعدادات المشروع الحالية. يوجد catch-all جذري؛ تطبيق ثغرات الكاش يتطلب فحص advisory وشروط SSG/ISR، فلا أسجل اختراق إنتاج مؤكدًا.

الإجراء الأول: تحديث Next.js وeslint-config-next إلى إصدار متوافق مصحح في تغيير مستقل، وتحديث lockfile، وفحص build واختبارات الخطأ والدخول والcatch-all. لم أطبق تحديث اعتماديات أوسع دون مراجعة توافقه.

APP_URL يحدد البوابة والSecure وHSTS؛ headers تُبنى وقت build. يجب ضبطه وقت البناء والتشغيل. تحقق TLS على اتصال القاعدة موجود، لكن تطبيق صلاحيات دور القاعدة يحتاج تحقق staging. ثقة x-forwarded-for تعتمد على proxy يكتب العنوان الفعلي؛ لا يكفي مجرد وصول الترويسة.

CI يحتوي نسخًا ومراقبة ورصيد مزود، ولا يحتوي workflow للفحص الآلي للشفرة والاختبارات على كل PR. Actions وصورة postgres مثبتة بtags فقط؛ تثبيت commit/digest تحسين منخفض الأولوية. إشعارات GitHub تعتمد على إعدادات المالك؛ فشل workflow لا يثبت وصول بريد.

## 8. تعليمات تنفيذ جاهزة للمهام الباقية

### مهمة A — Next.js

أنت منفذ تحديث أمني لـClowzy. افحص package.json وlockfile وAGENTS.md ودليل الإصدار الحالي. حدّث next وeslint-config-next إلى إصدار مصحح متوافق، بدءًا من 16.3.8 المذكور في المصدر الرسمي أعلاه، بعد التأكد من توفره. لا تغيّر React أو المصادقة أو بيانات الإنتاج دون سبب مثبت. نفذ lint/typecheck/build والاختبارات، وفحص error boundary والcatch-all والدخول في preview. القبول: lockfile متسق، لا تنبيهات جديدة، ولا تغير في السلوك العام. أبلغ بالملفات والنتائج والحدود؛ توقف إذا المصدر أو الإصدار غير متاح بدل افتراضه.

### مهمة B — اتصال المواقع

أنت منفذ حماية SSRF. أصلح safeGet في src/lib/site-email.ts واختباراته. استخدم آلية اتصال تربط socket بعنوان عام فُحص، وتحفظ hostname والتحقق من TLS، وتعيد التحقق لكل redirect، وتحظر العناوين غير العامة ومسارات IPv6 الانتقالية المؤدية لعناوين داخلية. حافظ على استخراج الإيميلات والعقود الحالية. حد إجمالي للوقت والبايتات، وإلغاء DNS/الطلبات عند انتهاء الميزانية. اختبر DNS rebinding وredirect داخلي وIPv4-mapped وTLS وtimeout محليًا بلا استغلال حي. لا تضف اعتمادًا إلا إذا native/المثبت لا يكفي. القبول: لا lookup مختلف عند الاتصال، ولا اتصال داخلي، ولا تعطيل تحقق الشهادة. أبلغ بالdiff والاختبارات؛ توقف عند غياب آلية اتصال قابلة للتحقق.

### مهمة C — التزامن الحقيقي

أنت منفذ تحقق مصادقة ورصيد. استخدم Store وDb والاختبارات الحالية في قاعدة PostgreSQL معزولة فقط. اختبر دخولًا يتداخل مع تغيير password، رابطَي reset متزامنين، reset مقابل changePassword، إلغاء الحساب مقابل إصدار جلسة، وحجزين مقابل الرصيد. لا تستخدم DATABASE_URL للإنتاج؛ توقف إذا لم تتأكد من البيئة. القبول: رابط جديد واحد فعال، كلمة قديمة لا تصدر جلسة بعد الإلغاء، لا deadlock، لا خصم مزدوج. نظف البيانات المؤقتة وأبلغ نتائج كل حالة بلا أسرار.

### مهمة D — بحث مستقل وموزع
